# MuseMate — AI 도슨트 리얼타임 시스템 개선 과제

**대상**: 풀스택 엔지니어 · **제한 시간**: 3시간 · **제출물**: 이 레포를 확장한 결과물

English version: [README.en.md](README.en.md)

## 배경

MuseMate는 박물관 방문객이 전시품 앞에서 웹페이지를 열면, AI 도슨트 "뮤즈"가
음성으로 인사하고 질문에 답해주는 서비스입니다.

현재 시스템(v1)은 동작은 하지만, 출시 후 두 가지 문제가 계속 지적되고 있습니다.

1. **접속 후 침묵.** 방문객이 페이지를 열고 나서 도슨트가 첫 마디를 하기까지
   몇 초간 아무 소리도 나지 않습니다. 인사말 준비(TTS)가 세션 연결 이후에,
   매 접속마다 처음부터 실행되기 때문입니다. 데모(`http://localhost:8080`)에서
   직접 체감해 보세요 — 타임스탬프가 찍힙니다.
2. **한국어 전용.** 외국인 방문객 비중이 늘고 있는데 v1은 한국어가 하드코딩되어
   있습니다. 전시 데이터에는 이미 전시별 지원 언어(`supported_langs`)와 언어별
   인트로 텍스트가 들어 있습니다.
3. **아무나 쓸 수 있음.** 서비스는 공개망에 있는데 v1에는 인증이 없어서, 입장권
   없이도 도슨트를 쓸 수 있습니다. v2부터는 입장 시 발급되는 **티켓 토큰**이
   있어야만 쓸 수 있어야 합니다.

당신의 임무는 이 시스템을 **v2로 진화**시키는 것입니다. 단, v1 클라이언트는
이미 배포되어 있어서 **v1 프로토콜은 계속 동작해야 합니다.**

## 현재 시스템

```
[브라우저] ──WS──> [legacy-server :8080] ──HTTP──> [mock-upstream :9000]
                    v1 프로토콜                      전시 데이터 / LLM / TTS
```

실행:

```bash
docker compose up --build
# 데모: http://localhost:8080
# upstream API: http://localhost:9000 (GET /exhibits, GET /exhibits/{id}, POST /llm/chat, POST /tts)
```

- **`mock-upstream/`** — 전시 콘텐츠 DB + LLM + TTS를 흉내내는 외부 시스템입니다.
  실제 프로바이더처럼 **지연이 있습니다** (LLM 첫 토큰 ~1.2초, TTS ~1.5초+텍스트 길이 비례).
  **수정 금지** — 여러분이 통제할 수 없는 외부 서비스라고 생각하세요.
  - 자가 검증용 도구: `GET /stats` 는 지금까지의 LLM/TTS 호출 횟수를 돌려주고
    `POST /stats/reset` 으로 초기화합니다. 캐시·요청 병합이 실제로 동작하는지
    확인할 때 쓰세요. `FAIL_RATE` 환경변수(0~1)를 주면 upstream이 확률적으로
    500을 반환해, 장애 상황을 시험해볼 수 있습니다.
- **`legacy-server/`** — v1 서버입니다. 유지·확장·랩핑·대체 모두 자유입니다.
  단, 파일 상단에 적힌 v1 프로토콜이 기존 클라이언트에게 계속 동작해야 합니다.

## 과제

### 1. 설계 문서 — `DESIGN.md` (필수)

v2 설계를 문서로 남기세요. 장문일 필요 없습니다(불릿 환영). 반드시 다룰 것:

- 접속 후 침묵을 없애기 위한 구조 변경과 그 근거
- 캐싱 전략: 무엇을, 어떤 키로, 언제까지 캐시하고, 언제 무효화하는가.
  동시에 같은 것을 요청하는 트래픽(단체 관람객 입장)은 어떻게 처리하는가
- **응답 지연 개선안**: v1은 답변 시 LLM 전체 완료 → TTS 완료를 직렬로 기다립니다
  (첫 오디오까지 ~6초). 첫 오디오까지의 시간을 구조적으로 줄이는 방법을
  설계하세요 (예: 문장 단위 TTS 파이프라이닝과 순서 보장). 구현은 보너스지만
  설계는 필수입니다.
- **서비스 경계와 스케일아웃**: 인사말 API를 대화 서버 안에 둘 것인가, 별도
  서비스로 분리할 것인가 — 근거와 함께. 그리고 여러분의 서버가 3대로 늘어나면
  무엇이 깨지는가 (캐시는 어디에 있어야 하는가, 세션 상태는?)
- 다국어를 프로토콜에 어떻게 표현하는가
- **인증**: 토큰을 어디서 검증하는가(연결 시점 vs 메시지별), 실시간 채널에는
  토큰을 어떻게 싣는가(query string? header? 첫 프레임?)와 각 방식의 트레이드오프
- v1 호환을 어떻게 유지하는가 (버저닝 방식)
- 주요 실패 모드와 그 처리 (upstream 장애, 지원하지 않는 언어 등 —
  `FAIL_RATE`로 직접 시험해볼 수 있습니다)
- 시간이 없어 구현하지 못한 것과 그 이유

### 2. 백엔드 (필수 — 이 과제의 중심)

- **인사말 API**: 세션 연결 없이 인사말(텍스트+오디오)을 받아올 수 있는 HTTP
  엔드포인트를 설계·구현하세요.
  - 반복 요청이 빨라야 합니다 (캐싱 — 인메모리 허용, 키 설계가 중요합니다).
  - **동시 요청 병합**: 콜드 캐시 상태에서 같은 인사말 요청 N개가 동시에
    들어와도 upstream TTS 호출은 **1회**여야 합니다. (`POST /stats/reset` 후
    동시 요청을 보내고 `GET /stats`로 직접 확인해 보세요 — 평가자도 같은
    방법으로 확인합니다.)
  - 없는 전시, 지원하지 않는 언어 등의 에러 응답을 포함하세요.
- **v2 리얼타임 채널**: 언어를 지정해 대화할 수 있고, 연결 시점에 침묵을 만들지
  않는 v2 세션 프로토콜을 설계·구현하세요.
  - 전송 방식은 강제하지 않습니다 — WebSocket, SSE, HTTP 스트리밍, gRPC, 그 외
    무엇이든 좋습니다. 제약은 두 가지뿐입니다: 여러분의 페이지(브라우저)에서
    실제로 시연할 수 있을 것, 그리고 선택의 근거(대안 대비 트레이드오프)를
    DESIGN.md에 적을 것. 우리는 선택이 아니라 근거를 채점합니다.
  - 프레임에 타입 구분이 있어야 하고, upstream 실패가 클라이언트에 구조화된
    에러로 전달되어야 합니다.
- **티켓 인증**: 방문객은 발급받은 티켓 토큰으로만 v2를 쓸 수 있어야 합니다.
  - 토큰 발급 엔드포인트를 만드세요. 가짜 로그인이면 충분합니다 — 서명된 토큰이면
    형식은 자유(자체 HMAC, JWT 등), 비밀키는 환경변수로. 외부 IdP는 필요 없습니다.
  - 인사말 API와 v2 채널은 유효한 토큰 없이는 거부해야 합니다 — HTTP는 401,
    실시간 채널은 **연결 시점에** 거부.
  - 클라이언트가 메시지 안에서 주장하는 identity를 신뢰하면 안 됩니다. 세션의
    주인이 누구인지는 검증된 토큰이 결정합니다.
  - v1은 인증 없이 그대로 둡니다 (기존 배포 클라이언트 호환).
- v1 프로토콜은 계속 동작해야 합니다.

### 3. 프론트엔드 (필수 — 최소)

이 과제의 중심은 백엔드입니다. 프론트는 여러분의 v2를 실제로 시연할 수 있는
**최소한의 페이지**면 충분합니다 — 프레임워크 없이 legacy 데모 수준의 단일
HTML이어도 됩니다.

- 전시 선택 + 언어 선택 → 접속하면 **도슨트의 인사말이 지체 없이 재생**되고,
  이어서 대화할 수 있어야 합니다. (인사말 준비와 세션 연결은 동시에
  진행되어야겠죠.)
- 접속 전에 티켓 토큰을 발급받아 사용하세요. 발급 UI는 자동이어도 됩니다
  (페이지 로드 시 자동 발급 등 — 로그인 화면을 만들 필요 없습니다).
- 오디오가 겹쳐 재생되지 않아야 합니다.
- 스타일링은 평가하지 않습니다.

### 4. 실행 환경 (필수)

- `docker compose up --build` **한 번으로 전체 시스템이 뜨고**, 평가자가
  `http://localhost:3000` 에서 여러분의 위젯을 바로 사용할 수 있어야 합니다.
- 별도 수동 단계(로컬 npm install, env 파일 작성 등)가 필요하다면 감점입니다.
  필요한 설정은 compose 안에서 해결하세요.

### 보너스 (필수 과제가 끝났을 때만)

- DESIGN.md에 설계한 응답 지연 개선안(문장 단위 TTS 파이프라이닝 등)의 실제 구현
- upstream 장애 시의 우아한 실패 (`FAIL_RATE=0.3` 으로 시험 — 예: TTS 실패 시
  텍스트만이라도 전달)
- 대화 중 언어 전환 (진행 중인 응답/오디오 처리 포함)
- 인사말 재생 중 사용자가 입력을 시작하면 인사말을 중단하는 처리
- 응답 텍스트의 점진(스트리밍) 렌더링
- 연결 끊김 시 재연결
- 핵심 로직 테스트

## 규칙

- **제한 시간 3시간.** 완성도보다 우선순위 판단을 봅니다. 못 한 것은 감추지 말고
  DESIGN.md에 적으세요 — "무엇을 포기했고 왜"가 중요한 평가 항목입니다.
- `mock-upstream/`은 수정 금지. 나머지는 전부 자유입니다.
- 지원자 구현 언어/스택은 자유입니다 (compose로 실행만 되면 됩니다).
- AI 코딩 도구 사용은 자유입니다. 사용했다면 어떻게 활용했는지 DESIGN.md에
  한두 줄로 적어주세요.
- 커밋을 작업 단위로 남겨주세요. 커밋 히스토리도 함께 봅니다.

## 평가 기준 (요약)

| 영역 | 비중 | 보는 것 |
|---|---|---|
| 설계 | 30% | 원인 진단, 캐시 키/무효화, 응답 지연 개선안, 버저닝, 트레이드오프 근거 |
| 백엔드 | 40% | 인사말 API(캐시·동시 요청 병합), v2 채널, 티켓 인증, 에러 처리, 코드 구조 |
| 프론트엔드 | 15% | v2 시연 가능 여부, 인사말 병렬 로드·즉시 재생, 오디오 겹침 없음 |
| 실행 재현성 | 15% | compose 한 번에 뜨는가, 문서와 실제의 일치 |

행운을 빕니다. 🏺
